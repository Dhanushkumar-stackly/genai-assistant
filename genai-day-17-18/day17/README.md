## 1. Day 17 Objective

The objective of Day 17 is to integrate **voice input** into the existing GenAI Assistant backend.

The implementation accepts an audio file, validates it, converts the audio into text using an STT provider, sends the cleaned transcript to the **existing `/ask` RAG service**, records stage-level performance logs, and validates the complete voice-input flow through automated tests.

### Overall Flow

```text
User
  ↓
Audio File Upload
  ↓
Audio Validation
  ├── File Type Validation
  ├── File Size Validation
  └── Empty File Validation
  ↓
Speech-to-Text (STT)
  ↓
Transcript Cleaning
  ↓
Existing /ask Endpoint
  ↓
Existing RAG Service
  ↓
Grounded Answer + Sources
  ↓
Stage-Level Logging
  ↓
Response to User
```

# 3. Task 1 — Create Audio Input Path

## Objective

Create an API endpoint that accepts an audio file from the user.

The endpoint validates:

* File existence
* File type
* File size
* Empty audio input

### Supported Audio Types

```text
audio/wav
audio/x-wav
audio/mpeg
audio/mp4
audio/x-m4a
audio/webm
```

### Maximum File Size

```text
5 MB
```

---

## Endpoint

```http
POST /voice/input
```

### Example Request

```bash
curl -X POST "http://127.0.0.1:8000/voice/input" \
  -F "file=@sample.wav"
```

### Expected Response

```json
{
  "request_id": "generated-request-id",
  "status": "accepted",
  "filename": "sample.wav",
  "content_type": "audio/wav",
  "size_bytes": 12345,
  "message": "Audio input accepted"
}
```

---

## Validation

### Valid Audio

```text
Status: 200
Result: Accepted
```

### Empty Audio

```text
Status: 400
Result: Rejected
```

### Unsupported File Type

```text
Status: 415
Result: Rejected
```

### File Larger Than 5 MB

```text
Status: 413
Result: Rejected
```

# 4. Task 2 — Speech-to-Text / Transcription

## Objective

Convert the validated audio input into text using an STT provider.

The implementation supports:

* Demo STT provider
* OpenAI STT provider
* STT latency measurement
* Provider error handling
* Language information when available

---

## Endpoint

```http
POST /voice/transcribe
```

### Example

```bash
curl -X POST "http://127.0.0.1:8000/voice/transcribe" \
  -F "file=@sample.wav"
```

### Example Response

```json
{
  "request_id": "generated-request-id",
  "status": "transcribed",
  "filename": "sample.wav",
  "content_type": "audio/wav",
  "size_bytes": 12345,
  "transcript": "What is the leave policy?",
  "language": "en",
  "stt_latency_ms": 123.45,
  "provider": "demo"
}
```

---

## STT Provider Configuration

The provider is controlled using:

```text
STT_PROVIDER
```

### Demo Mode

```env
STT_PROVIDER=demo
```

Demo mode is useful for local testing because it does not require an external STT service.

### OpenAI Mode

```env
STT_PROVIDER=openai
OPENAI_API_KEY=<your-api-key>
```

**Never commit API keys to Git.**

# 5. Task 3 — Connect Voice Input to Existing `/ask`

## Objective

The transcript generated by STT must be passed to the **existing question-answering/RAG service**.

A separate RAG implementation must NOT be created for voice input.

### Flow

```text
Audio
 ↓
STT
 ↓
Transcript
 ↓
Clean Transcript
 ↓
Existing /ask
 ↓
Existing RAG
 ↓
Answer + Sources
```

---

## Endpoint

```http
POST /voice/ask
```

### Example Request

```json
{
  "transcript": "   What is the leave policy?   "
}
```

The transcript is cleaned before being sent to `/ask`.

### Cleaning

Input:

```text
"   What is the leave policy?   "
```

Output:

```text
"What is the leave policy?"
```

Whitespace is normalized and empty transcripts are rejected.

---

## Example Response

```json
{
  "status": "answered",
  "question": "What is the leave policy?",
  "answer": "Answer based on document: company_policy.pdf",
  "sources": [
    {
      "document_id": "document-id",
      "title": "company_policy.pdf",
      "score": 1.0
    }
  ],
  "rag_latency_ms": 15.23
}
```

# 6. Task 4 — Stage-Level Logging

## Objective

Track the performance and status of each stage in the voice pipeline.

The logging system records:

* Request ID
* Audio filename
* Content type
* Audio size
* Transcript
* STT latency
* RAG latency
* Total latency
* Failed stage
* Request status
* Error information

---

## Log Location

```text
logs/voice_requests.jsonl
```

Each request is stored as a JSON object on a separate line.

### Example

```json
{
  "request_id": "abc123",
  "filename": "sample.wav",
  "content_type": "audio/wav",
  "size_bytes": 12345,
  "transcript": "What is the leave policy?",
  "stt_latency_ms": 120.5,
  "rag_latency_ms": 25.4,
  "total_latency_ms": 150.2,
  "stage": "rag",
  "status": "success",
  "error": null
}
```

---

## Transcript Redaction

Sensitive terms are redacted before logging.

Example:

```text
"My password is abc123"
```

becomes:

```text
"My [REDACTED] is abc123"
```

The purpose is to reduce the risk of sensitive information being unnecessarily stored in application logs.

# 7. Task 5 — Voice Input End-to-End Testing

## Objective

Verify that the complete voice pipeline handles different audio conditions and failure scenarios.

---

## Test Scenarios

### 1. Clear Audio

```text
Input: Clear speech
Expected: Successful transcription
```

### 2. Mild Background Noise

```text
Input: Speech with mild background noise
Expected: Transcription should still be processed
```

### 3. Domain-Specific Terms

```text
Input: Technical/company-specific terminology
Expected: STT should produce a usable transcript
```

### 4. Empty Audio

```text
Input: Empty file
Expected: HTTP 400
```

### 5. Unsupported File Type

```text
Input: .txt file
Expected: HTTP 415
```

### 6. Voice/Text Equivalence

The same question should produce equivalent cleaned questions.

Example:

```text
Voice:
"What is the leave policy?"

Text:
"What is the leave policy?"
```

Expected:

```text
Same grounded question
```

### 7. Grounded Answer Equivalence

Voice and equivalent text input should return:

```text
Equivalent answer
+
Equivalent source/evidence
```

This verifies that voice input does not introduce a separate or inconsistent RAG implementation.

# 17. Error Handling

The implementation identifies failures according to the responsible processing stage.

### Audio Validation Failure

```text
Stage: validation
```

### STT Failure

```text
Stage: stt
```

### RAG Failure

```text
Stage: rag
```

This makes debugging easier because the application can distinguish between:

```text
Audio problem
       ↓
STT problem
       ↓
RAG problem
```

instead of returning one generic error.
